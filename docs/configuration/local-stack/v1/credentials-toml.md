# `credentials.toml` reference

`credentials.toml` contains **references to credentials**, never credential values. File entries point to capability files. Opaque entries name Gongbu-owned Keychain service/account coordinates that the owning service resolves at runtime.

> Never paste a bearer token, API key, approval capability, reconciliation capability, or credential-file content into this file.

## Top-level field

### `schema_version`

| Attribute | Value |
| --- | --- |
| Required | Always |
| Supplied by | Generated by Hubu |
| Type | Integer |
| Supported value | `1` |
| Sensitive | No |

All three source files must use a supported source schema version. Unknown fields are rejected.

## `[files]`

The four file entries are required for the schema-version-1 client handoff. Each value must be a safe absolute path to an existing regular file. The paths must refer to distinct capabilities.

The renderer checks the paths and owning service contracts but does not read, copy, compare, hash, log, or serialize the credential values.

### `files.hubu_auth`

| Attribute | Value |
| --- | --- |
| Required | Always |
| Supplied by | Generated by Hubu bootstrap |
| Value | Absolute path to the Hubu authentication bearer capability file |
| Used by | Hubu CLI and unified MCP protected Hubu calls |

```toml
[files]
hubu_auth = "/absolute/path/to/hubu.auth-token"
```

Copy the path configured for `HUBU_AUTH_TOKEN_FILE`; do not copy the file's content.

### `files.hubu_approval`

Absolute path to the human approval capability file configured for Hubu. This is intentionally distinct from ordinary Hubu authentication because approval authority must not be collapsed into a general bearer capability.

### `files.hubu_reconciliation`

Absolute path to the reconciliation capability file configured for Hubu. Reconciliation authority is separate from authentication and approval authority.

### `files.gongbu_caller`

Absolute path to the Gongbu caller bearer capability used by the unified MCP handoff. This is the client-side reference for authenticated Gongbu calls; it authenticates the installation/service and carries no execution account or agent claim. It is not the provider credential and not the Keychain coordinate used by Gongbu server configuration.

## `[opaque.<key>]`

Opaque tables are a map keyed by a local, operator-chosen reference name. The key is referenced from generated Gongbu configuration or `providers.toml`; it is not itself a secret.

```toml
[opaque.provider_image]
service = "gongbu.provider.example"
account = "local-image-provider"
```

The renderer never resolves these coordinates. Gongbu owns Keychain access, credential loading, and provider use.

### `opaque.<key>.service`

| Attribute | Value |
| --- | --- |
| Required | For every declared opaque reference |
| Supplied by | Defined by Gongbu credential setup or chosen by the operator |
| Meaning | Non-empty Keychain service coordinate |
| Sensitive | Reference metadata; do not treat it as the secret |

Use the exact service name under which the owning Gongbu process can retrieve the credential. Do not place the credential value here.

### `opaque.<key>.account`

| Attribute | Value |
| --- | --- |
| Required | For every declared opaque reference |
| Supplied by | Defined by Gongbu credential setup or chosen by the operator |
| Meaning | Non-empty Keychain account coordinate within the selected service |

The `service` and `account` pair must uniquely identify the intended credential revision according to the operator's Keychain practice.

## Reserved managed-Gongbu references

Managed Gongbu requires these exact local keys:

### `opaque.gongbu_hubu`

Keychain coordinate for the Hubu capability used by Gongbu server when it calls Hubu's versioned executor lifecycle interface. It must correspond to the server-side Hubu capability expected for that caller.

```toml
[opaque.gongbu_hubu]
service = "gongbu.hubu"
account = "local-stack"
```

### `opaque.gongbu_caller`

Keychain coordinate for the bearer capability Gongbu server expects from its authenticated installation caller. The capability carries no execution identity. This server-owned reference and `files.gongbu_caller` are separate references on opposite sides of the authentication boundary.

The renderer does not prove that their underlying values match. When rotating the shared capability, update both owning references before the whole-stack stop/start cycle.

## Provider credential references

Live `providers.toml` targets use the opaque table key:

```toml
# credentials.toml
[opaque.provider_image]
service = "gongbu.provider.example"
account = "image-production"

# providers.toml
[[targets]]
credential = "provider_image"
```

Every referenced key must exist and contain non-empty `service` and `account` fields. Multiple targets may refer to an intentionally shared credential, but provider selection and revision semantics remain explicit in each target.

## Rotating a file reference

Do not overwrite a credential value in place. Rendering authenticates source references, not the bytes stored behind them, so in-place replacement is not a detectable or supported rotation.

1. Create the replacement credential file with operator-controlled permissions.
2. Change only the absolute path in `credentials.toml`.
3. Run doctor and render.
4. Review the changed source file, affected components, and generation ID.
5. Stop the whole managed stack, activate the reviewed generation, and start it.
6. Keep the previous credential available until the new generation is running and verified.
7. Rerun `hubu init codex --stack-profile ...` when the client handoff is affected.

## Rotating an opaque reference

Create a new Keychain item or coordinate according to Gongbu's credential procedure, then change the `service` and/or `account` reference. Do not copy Keychain values into TOML. Keep the previous item until the reviewed generation is active and verified.

## Common mistakes

- Pasting a token after `hubu_auth =` instead of its absolute file path.
- Reusing one capability file for authentication, approval, and reconciliation.
- Assuming `files.gongbu_caller` and `opaque.gongbu_caller` are interchangeable.
- Referencing `[opaque.provider_image]` as `credential = "opaque.provider_image"`; the correct key is `credential = "provider_image"`.
- Deleting the previous credential before the replacement generation is running.
