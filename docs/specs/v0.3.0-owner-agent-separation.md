# v0.3.0 tech spec: owner and agent separation

| | |
| --- | --- |
| Release | v0.3.0 (Aegislash) |
| Status | Draft for review |
| Design | [Hubu v0.3 Design](https://claude.ai/artifact/WheHDsTMEYncfaei5K7WqZ) |
| Linear | [v0.3.0 (Aegislash): Owner & Agent Separation](https://linear.app/hubu/project/v030-aegislash-owner-and-agent-separation-4520f17be2ce) |
| Baseline | `main` at `d0ceef0`, plus PR #423 (HUB-345) and the HUB-344 findings |

This spec records the technical decisions for v0.3.0. The design doc says what
the release must achieve and why; this document says how, precisely enough that
parallel agents implementing different issues make the same choices. Where an
issue and this spec disagree, this spec wins and the issue is updated.

## 1. Goal and threat model

After v0.3.0, an agent with a shell running as the owner's macOS user cannot
raise a budget, change policy, approve spend or reconcile. The adversary is
mistaken or prompt-injected, not an exploit author. It can read every file in
the profile folder, run any local command, and call any local HTTP port.

The rule: **owner actions need the owner's physical presence, confirmed by
`hubu-server` itself.** Holding a file is never enough.

Out of scope for v0.3.0, and stated as known limits in section 13: agent
isolation between harnesses (v0.3.1), executor routes and provider keys
(v0.3.2), and direct database edits (v0.3.3).

## 2. Starting point

PR #423 (HUB-345) introduces two credential classes and a route table:

- `CredentialClass::{Owner, Agent}`, classified by token hash in
  `LocalAuth::classify`.
- `RouteAccess::{Agent, Owner, Executor}` declared per route in
  `ROUTE_ACCESS` (`crates/hubu-api/src/lib.rs`). Undeclared routes default to
  owner-only, and a test fails if a route is added without a declaration.
- The agent credential is a separate file (`hubu.agent-token`, or
  `state/credentials/hubu/agent` in a managed profile, or
  `files.hubu_agent` for external profiles). `hubu init codex` hands only the
  agent credential to the unified MCP.
- Rejections use HTTP 403 with `error_code: owner_authority_required` and
  `retry_guidance.action: ask_owner`.

What PR #423 does not change, and this spec does: the owner bearer, the
approval capability and the reconciliation capability are still files that a
same-user agent can read and present.

## 3. Credential model

| Credential | Held by | Stored | Grants |
| --- | --- | --- | --- |
| Agent credential | Unified MCP, agent CLI use | File, `0600` | `Agent` routes only |
| Owner bearer | `hubu` CLI, `hubu ui` | File, `0600` | Owner identity on the transport. Owner reads and tightening. Each owner action only together with the owner's confirmation of that action (section 5). |
| Owner confirmation | Not stored | — | Exactly the one action (or approval set) its dialog names |
| Executor credential | Gongbu | Unchanged in v0.3.0 (the owner bearer) | `Executor` routes. Replaced in v0.3.2. |
| Approval capability | — | Retired | Replaced by owner confirmation |
| Reconciliation capability | — | Retired | Replaced by owner confirmation |

**Decision: the owner bearer stays a file.** It identifies the owner's tools on
the loopback transport and gates owner reads. It no longer carries authority
on its own, so an agent that reads it gains owner reads and tightening (which
removes authority, section 5.5) but no owner actions.
Removing the file would add work and remove no risk, because the authority now
lives in the owner's confirmation of each action.

## 4. Route access

`RouteAccess::Owner` is split into two variants. The full table after v0.3.0:

```rust
enum RouteAccess {
    Agent,       // agent or owner credential
    OwnerBearer, // owner bearer; never prompts
    OwnerAction, // owner bearer + the owner's confirmation of this action
    Executor,    // owner bearer until v0.3.2
}
```

| Access | Routes |
| --- | --- |
| `Agent` | `POST /spend/authorize`, `POST /spend`, `POST /spend/void`, `GET /spend/approval`, `POST /spend/approval/prompt`, `GET /budgets`, `GET /ledger`, `GET /ledger/transactions`, `GET /ledger/summary`, `GET /spend/authorizations`, `GET /spend/authorizations/show`, `GET /watch`, `GET /agents`, `GET /user`, `GET /policies`, `GET /policies/show`, `POST /agents/register`, `GET /owner/presence` |
| `OwnerBearer` | Reads: `GET /users`, `GET /user/spending-target`, `GET /agents/history`, `GET /policies/export`, `GET /policies/history`, `GET /policies/diff`, `GET /budgets/{budget_id}/versions`, `GET /governance/summary`, `GET /governance/records`, `GET /governance/records/{record_id}`, `GET /governance/owner-presence`. Tightening writes: `POST /budgets/revoke`, `POST /user/spending-target/revoke`, `POST /spend/approval/resolve` with `decision: deny` |
| `OwnerAction` | `POST /init`, `POST /user/spending-target`, `POST /agents/rename`, `POST /policies`, `POST /budgets`, `POST /budgets/{budget_id}/versions`, `POST /spend/approval/resolve` with `decision: approve`, reconciliation through `POST /spend/executor/settle` and `/release` with a reconciliation body, `POST /spend/approval/resolve-batch` (section 5.8, HUB-399) |
| `Executor` | `POST /spend/executor/validate`, `/resolve`, `/claim`, `GET /spend/executor/claim`, `GET /spend/executor/reconciliation`, `POST /spend/executor/settle`, `/release` with an executor body |

Rules:

- `GET /owner/presence` and `GET /governance/owner-presence` are new in v0.3.0
  (sections 5 and 9). There are no lock or unlock routes, because there is no
  owner window (section 5.3).
- Undeclared routes default to `OwnerAction`, the strictest class. A request
  to an undeclared path is refused with `no route` before any prompt, so the
  owner is never asked about it.
- `POST /spend/approval/resolve` is declared `OwnerAction`, and the handler
  lowers `decision: deny` to `OwnerBearer`, the same way the body decides the
  class for reconciliation below. The route sweep (section 13) covers both
  bodies.
- Reconciliation shares a path with executor settlement. The request body
  decides the class: `ExecutorSpendFinalizationHttpRequest::Reconciliation`
  is an owner action, `::Executor` stays on the executor class.
- New error codes, all HTTP 403 unless noted, each with `retry_guidance`:
  - `owner_authority_required`: agent credential on an owner route (unchanged).
  - `owner_presence_required`: owner action, and the request sent
    `X-Hubu-No-Prompt` (section 5.4).
  - `owner_presence_denied`: the owner refused, or the dialog failed.
  - `owner_presence_timeout`: no answer within the prompt timeout.
  - `owner_presence_unavailable`: no presence provider can run (section 5.2).
  - HTTP 409 `owner_prompt_in_progress`: another prompt is on screen.
  - HTTP 429 `owner_prompt_rate_limited`: see section 5.7.
  - HTTP 409 `approval_not_pending`: `POST /spend/approval/prompt` or a
    queued CLI approval on a request that is already resolved (section 5.6).

## 5. Owner presence

### 5.1 Interface

```rust
pub trait PresenceProvider: Send + Sync {
    /// Blocks until the owner answers, the timeout passes, or the prompt fails.
    fn confirm(&self, request: &PresenceRequest) -> PresenceOutcome;
    fn method(&self) -> PresenceMethod;
}

pub struct PresenceRequest {
    pub reason: String,         // built by Hubu, never by the caller (5.5)
    pub timeout: Duration,      // default 60 s
}

pub enum PresenceOutcome {
    Confirmed { method: PresenceMethod },
    Denied,                     // includes UserCancel, AppCancel, SystemCancel
    TimedOut,
    Unavailable(String),        // provider cannot run here
}

pub enum PresenceMethod { Biometric, DevicePassword, Fixture }
```

Every outcome other than `Confirmed` is treated as a refusal. There is no path
from an error to an approval.

### 5.2 Providers

- **macOS LocalAuthentication** (default on macOS). Uses
  `objc2-local-authentication` 0.3.2, as HUB-344 established. Default policy
  `DeviceOwnerAuthentication`: Touch ID, or the login password when Touch ID
  is unavailable, locked out, or the lid is closed. `HUBU_OWNER_PRESENCE_POLICY=biometrics`
  selects `DeviceOwnerAuthenticationWithBiometrics` instead, with no password
  fallback. The setting is read at server start only. The cancel button title is
  "Deny". Add the five crates to the existing objc2 case in
  `scripts/generate-third-party-licenses.sh`.
- **Fixture** (tests and proof kits only). Answers from a script. Enabled only
  by `HUBU_OWNER_PRESENCE_PROVIDER=fixture`, and `hubu-server` refuses to start
  with it when the database path is inside a managed profile. `hubu stack
  doctor` reports it if set. It exists so CI and Break Hubu can run owner steps
  against released binaries.
- **None.** When no GUI session exists (for example `hubu-server` started over
  SSH with no Aqua session), the macOS provider returns `Unavailable` and owner
  actions fail with `owner_presence_unavailable`. A typed-passphrase provider
  is not part of v0.3.0.

HUB-344's owner check (2026-11-18, macOS 26.4) confirmed the dialog appears
from a background process started by launchd with no terminal, works under ad
hoc signing with the hardened runtime, and closes as a deny when Hubu calls
`invalidate()`. The dialog names the executable, so it reads `"hubu-server" is
trying to …`. That is acceptable for v0.3.0; an app bundle named "Hubu" can come
later. Deny, lid closed and SSH were not run and are covered by the manual
check (section 13).

`hubu-server` must run in the owner's GUI session for the dialog to appear.
`hubu stack start` already spawns it as a child of the owner's process, which
satisfies this.

New requirement: the installed `hubu-server` and `hubu` binaries are ad hoc
signed with the hardened runtime (`codesign -s - -o runtime`). This blocks
`DYLD_INSERT_LIBRARIES` and debugger attach. Nothing signs binaries today, so
the install and upgrade path (release archive script and the local upgrade
skill) must add this step, and `hubu stack doctor` reports a binary without it.

### 5.3 No owner window (decided 2026-11-19)

Earlier drafts opened a five-minute owner window after one confirmation. The
owner (`hacker-no-ice`) dropped it on 2026-11-19:

- **Consent must match the dialog.** The dialog names one action, so a
  confirmation must not authorize anything else. A window made "set
  design-agent's budget to 20.00 USD" silently allow any owner action for five
  minutes.
- **It helped the adversary.** The confirmation's window token went to whoever
  made the request. An agent that read the owner bearer and got the owner to
  confirm one action would have held five minutes of unprompted owner actions.
- **It saved little.** The CLI prompts per action anyway, every approval
  prompted even inside a window, and tightening never prompts. Floods of
  approvals are handled by batch approval (section 5.8).

So every owner action prompts once, and one confirmation authorizes exactly
that action. The server keeps no owner authority between requests. A restart
loses nothing.

### 5.4 Prompting on demand

An owner action that arrives with the owner bearer prompts inline: the server
builds the reason (section 5.5), raises the dialog and holds the HTTP request
until the outcome or the timeout. On `Confirmed` it performs the action.

**Dialog first (decided 2026-11-19).** The server checks only what the dialog
text needs: the request parses, the amounts in the text parse, and the named
agent, budget, approval or route exists. A request without those is refused
with no dialog. Everything else stays in the handler, unchanged, and runs after
confirmation; a request that fails there returns the handler's error and
writes nothing. The owner may therefore confirm a request that then fails.
Validation is not duplicated before the dialog. Moving all stateless checks
ahead of it needs handlers split into prepare and execute (HUB-400).

For spend approvals the dialog appears only after the policy engine returned
`needs_approval` and the pending request was saved. After confirmation the
approval checks (still pending, budget active, enough balance) run before any
budget hold or spend token is written.

A client may send `X-Hubu-No-Prompt: 1` to get `owner_presence_required`
instead of a dialog. Executors always send it (they never prompt the owner).

### 5.5 Dialog text

macOS renders the text as `"<app name>" is trying to <reason>.`, so every
reason is a verb phrase built by `hubu-server` from the stored, validated
request. Caller-supplied free text never appears in it.

| Action | Reason template |
| --- | --- |
| Approve spend | `approve {amount} on {provider_target} for agent {agent_name}` |
| Deny spend | No prompt (`OwnerBearer`) |
| Raise or set a budget | `set {agent_name}'s budget to {amount} (now {current})` |
| Create a budget | `create a {amount} budget for {agent_name}` |
| Revoke a budget | No prompt (`OwnerBearer`) |
| Revoke the spending target | No prompt (`OwnerBearer`) |
| Apply a policy | `apply policy revision {n} to {scope}` when the request sends `expected_revision`, otherwise `apply a new policy revision to {scope}` |
| Rename an agent | `rename agent {old} to {new}` |
| Spending target | `set the spending target to {amount}` |
| Reconcile a claim | `record claim {claim_id} as {billed or not billed}` |
| Initialize Hubu | `initialize Hubu for owner {username}` |
| Approve a batch (5.8) | `approve {n} spend requests: {total} for {agent_name}, … (largest {amount})` |

Agent names come from registration, which an agent controls. In reasons they
are reduced to `[A-Za-z0-9._-]`, at most 32 characters. Amounts use the
existing canonical money formatting with the upper-case currency, for
example `20.00 USD`. Currency input is accepted in any case, as the handlers
accept it.

Decision: **tightening needs the owner bearer only.** Denying a spend, revoking
a budget and revoking the spending target remove authority. They never prompt,
so the owner can always stop spending at once, from the portal or the CLI,
even when Touch ID is unavailable.

The cost: an agent that reads the owner bearer can also deny pending requests
and revoke budgets. That disrupts work but grants nothing, and every such call
is recorded with its client. Lowering a budget through a new version is not
treated as tightening; it goes through `POST /budgets/{budget_id}/versions` and
prompts like any budget change.

### 5.6 Spend approvals

- **Every approval prompts,** so the owner always sees the amount being
  approved.
- **Deny closes the request in every flow (decided 2026-11-19).** Pressing
  Deny in an approval dialog resolves the request as denied, whether the owner
  started it (portal, CLI, `POST /spend/approval/resolve` with `approve`) or
  an agent raised it from chat. A timeout, an unavailable provider, a busy
  screen or the rate limit leave it pending. Refusal responses carry the
  resulting `approval_status`.
- **Approving from chat (decided 2026-11-18).** The owner approves in chat as
  before, and the Touch ID dialog is what actually approves:
  1. A spend enters `needs_approval`. The agent tells the owner in chat.
  2. When the owner says yes, the agent calls `POST /spend/approval/prompt`
     with the `approval_request_id` (MCP tool `hubu_prompt_spend_approval`).
     This is an `Agent` route.
  3. `hubu-server` checks the request is still pending, then
     raises the approval dialog with the reason built from the stored request
     (section 5.5). It holds the HTTP request until the outcome or the 60 s
     timeout.
  4. `Confirmed` resolves the request as approved, and the response says so.
     The agent then continues the spend as it does after a portal approval
     today. Deny resolves it as denied and closes it. Timeout or
     `Unavailable` leaves it pending.
- **The agent can raise the dialog but never approve.** The owner's "yes" in
  chat carries no authority; only the dialog does. An agent that calls the
  route without asking only shows the owner a dialog they can deny.
- **Re-raising after being away.** Pending approval requests never expire:
  nothing sets a time limit on them, and they hold no budget. Only the 60 s
  dialog times out, and the request then stays pending. A pending request can
  be prompted again until it is resolved (approved or denied), so an owner who
  was away says yes when back and the agent raises it again. A denied request
  is closed and cannot be prompted; the agent must make a new spend request.
  Prompting a resolved request returns `approval_not_pending`.
- **The owner can also raise it.** The portal's pending list has an Approve
  button that prompts, and supports approving a selected set with one dialog
  (section 5.8). `hubu approvals` in the CLI walks pending requests oldest
  first, one dialog each, with "1 of 3" in the reason. These cover a finished
  agent session.
- **No automatic push.** `hubu-server` does not raise the dialog on its own when
  a spend enters `needs_approval`, because the owner may be away and the dialog
  would time out unseen. Hubu sends no notifications either: the owner's agent
  harness can (for example, a Codex post-tool-call hook that posts
  `needs_approval` results to Slack).

### 5.7 Abuse controls

- One dialog at a time. A second prompting request gets
  `owner_prompt_in_progress`.
- At most 5 **refused or timed-out** prompts per rolling 10 minutes across all
  clients (decided 2026-11-19). Beyond that, prompting requests get
  `owner_prompt_rate_limited` until the count over the last 10 minutes drops
  below 5, and the portal shows why. Confirmed prompts and prompts that could
  not be shown (`unavailable`) do not count: the limit stops an agent wearing
  the owner down, not the owner working through changes. Agent-raised approval
  prompts that are refused count. With the fixture provider the limit is off
  unless `HUBU_OWNER_PRESENCE_FIXTURE_RATE_LIMIT=on`.
- Every prompt is recorded (section 9), including refusals and timeouts, so
  an agent that keeps prompting is visible.

### 5.8 Batch approval (HUB-399)

When many requests wait for approval, the owner selects the ones to approve on
the portal and confirms them with one dialog.

- Route: `POST /spend/approval/resolve-batch`, `OwnerAction`, body
  `{ "approval_request_ids": [...], "decision": "approve" }` with 1 to 50 ids.
  A larger batch is refused before any prompt, and the client splits it. There
  is no batch deny: per-request deny never prompts (section 5.5).
- The set is fixed before the prompt. `hubu-server` builds the reason from the
  exact ids submitted: the count, per-currency totals per agent, and the
  largest single request. Unknown or foreign ids are refused before any prompt.
- After `Confirmed`, only ids that are still pending are approved. The response
  lists each id as `approved`, `skipped` (no longer pending, with its status)
  or `failed` (with the error). Ids outside the set are never touched.
- Deny closes every request in the set (section 5.6). A timeout or an
  unavailable provider leaves them all pending.
- One governance record for the prompt (action
  `spend.approval.approve_batch`, every id a target), plus the usual
  per-request approval lifecycle events.
- Safeguards against reflexive "select all": the portal selects nothing by
  default, groups requests by agent with group totals, and the dialog names the
  largest request.

## 6. Unified MCP (HUB-346)

The unified MCP holds only the agent credential. Tools that map to non-`Agent`
routes are removed, and `HUBU_MCP_TRUST_CLIENT_APPROVAL` is retired.

| Keep | Remove |
| --- | --- |
| `hubu_registration_guidance`, `hubu_register_agent`, `hubu_show_policy`, `hubu_submit_spend`, `hubu_authorize_spend`, `hubu_get_spend_approval`, `hubu_prompt_spend_approval` (new), `hubu_list_agents`, `hubu_list_budgets`, `hubu_list_ledger`, `hubu_list_authorization_records`, `hubu_get_authorization_record` | `hubu_list_users`, `hubu_register_human`, `hubu_apply_policy`, `hubu_policy_history`, `hubu_policy_diff`, `hubu_create_budget`, `hubu_revoke_budget`, `hubu_update_budget`, `hubu_budget_history`, `hubu_set_spending_target`, `hubu_revoke_spending_target`, `hubu_show_spending_targets`, `hubu_resolve_spend_approval`, `hubu_get_executor_claim`, `hubu_list_claims_requiring_reconciliation`, `hubu_reconcile_vendor_billed_claim`, `hubu_reconcile_vendor_did_not_bill_claim`, `hubu_governance_summary`, `hubu_list_governance_records`, `hubu_get_governance_record` |

`hubu_show_policy` uses `GET /policies/show`. Canonical YAML export uses the
owner-only `GET /policies/export` route and leaves the MCP surface.

`hubu_prompt_spend_approval` takes `approval_request_id`. Its description tells
the agent to call it only after the owner has said to approve in the
conversation, and that the owner confirms on the Mac.

A call to a removed tool name returns a tool error whose text says it is an
owner action done on the admin portal. Existing Codex configurations that set
the retired variable start normally and log once that it is ignored.

## 7. Admin portal (HUB-348)

- **Sign-in.** `hubu ui` prints a one-time login link. Opening it creates the
  session with the existing `HttpOnly; SameSite=Strict` cookie. Sign-in and
  reads need only the owner bearer, which the `hubu ui` process holds.
- **Actions.** The portal relays approvals, reconciliation and other owner
  actions with the owner bearer. The server prompts once with its own reason
  (section 5.4). The portal shows **Confirm on your Mac…** while waiting for
  the result, for up to the server's 60 s prompt timeout.
- **Pending approvals.** Approve or deny individual requests. Deny per request
  uses the owner bearer and never prompts. Batch selection follows with the
  route in section 5.8 (HUB-399).
- **Refusals.** Show the reason and next step for denials, timeouts, an
  unavailable provider, a prompt already open, rate limits and requests
  already resolved. Reload the pending list after an approval attempt to
  reflect the state described in section 5.6.
- The existing guards stay: loopback `Host`, origin checks, `X-Hubu-UI` header
  and JSON bodies for writes. Server-side owner presence replaces the
  browser confirmation header and the approval and reconciliation capabilities.

## 8. CLI (HUB-349)

- Each owner action prompts once (section 5.4). Tightening commands (`hubu budget revoke`, `hubu spend approval deny`,
  revoking the spending target) need no prompt (section 5.5). While waiting, the CLI prints `Waiting for the owner to confirm on this
  Mac…`. Refusals exit with status 3 and the error code.
- `--approval-token-file`, `--reconciliation-token-file`, `HUBU_APPROVAL_TOKEN`,
  `HUBU_APPROVAL_TOKEN_FILE`, `HUBU_RECONCILIATION_TOKEN` and
  `HUBU_RECONCILIATION_TOKEN_FILE` are accepted but ignored for one release,
  with a deprecation warning. Their removal is in the v0.3.3 cleanup pass.
- New `hubu approvals`: lists pending approval requests and raises the dialog
  for each, oldest first (section 5.6). The CLI sends the request's 1-based
  position and total as `X-Hubu-Approval-Position: position/total` on
  `POST /spend/approval/resolve`. The server appends the position to its reason
  for CLI approval requests using only the parsed positive integers. It skips
  the dialog if that approval is already resolved.
- The existing `hubu policy validate --path` command validates policy drafts
  offline. No new offline validation commands are needed (section 10).

## 9. Governance records

Add owner presence records (category `owner_presence`, read model below). One
record per prompt:

| Field | Value |
| --- | --- |
| `action` | Route and action kind, for example `budget.version.create` |
| `reason` | The exact reason text shown in the dialog |
| `outcome` | `confirmed`, `denied`, `timed_out`, `unavailable`, `rate_limited`, `superseded`, `not_required` (tightening, no prompt) |
| `method` | `biometric`, `device_password`, `fixture`, or null |
| `client` | `portal`, `cli`, `agent` (approval raised through `POST /spend/approval/prompt`), or `unknown` |
| `target` | Public ids of the budget, policy, agent or authorization concerned |

Tightening writes on `OwnerBearer` routes (section 4) raise no prompt, but each
one still writes an `OwnerPresence` record with `outcome: not_required`,
`method` null, and its `client`, so a tightening call made with a stolen owner
bearer is visible. Reads write no record.

Records are stored in an additive `owner_presence_records` table and read
through `GET /governance/owner-presence` (owner bearer, `limit` 1–200, newest
first), with `category: owner_presence` on each record. They are not mixed
into the lifecycle-fact read model of `GET /governance/records`, whose facts
need agent and account ids that a presence record does not have, and they need
no change to existing rows. A record is written on its own just before the
action it authorizes runs, or on its own when the prompt was refused. If it
cannot be written, the action does not run.

## 10. Drafts applied by the owner (HUB-350)

- **Policy files** use the existing policy YAML. `hubu policy validate --path
  PATH` runs the policy parser offline and prints the
  first error with its line.
- **Policy apply flow.** Load file → validate → show the diff against the
  current revision → owner
  clicks Apply → dialog with the reason from section 5.5 → applied.
- No route accepts a draft from an agent, and Hubu stores no drafts.

## 11. Overrides (HUB-351, cut candidate)

If built: a `governance_overrides` table keyed by action kind, all off by
default. Enabling one is an owner action with its own dialog reason (`allow
agents to {action} without you`). The never-delegable set is enforced in code,
not data: changing overrides, raising or creating a budget, approving spend,
reconciliation, applying a policy that loosens. Delegated actions are recorded
in governance with the override that allowed them. If cut, v0.3.0 ships Strict
with no override table.

## 12. Migration and compatibility (HUB-352)

On first start of v0.3.0 against a v0.2.5 profile:

1. Take the existing pre-migration backup.
2. Run the additive schema changes (section 9, and section 11 if built).
3. Generate the agent credential if absent (PR #423 already does this).
4. Stop reading the approval and reconciliation capability files in managed
   profiles. Leave them on disk; `hubu stack doctor` reports them as obsolete
   and safe to delete. Deletion is the v0.3.3 cleanup pass.
5. Rewrite the Codex MCP configuration written by `hubu init codex` so it
   references only the agent credential and drops the retired variable.

External profiles (`[files]` in `credentials.toml`):
- `files.hubu_agent` is required (PR #423).
- `files.hubu_approval` and `files.hubu_reconciliation` are accepted and
  ignored, with a warning.
- Owner presence works only if that `hubu-server` runs in a GUI session.
  Otherwise owner actions fail with `owner_presence_unavailable`, and the
  upgrade guide says so.

`docs/operations/upgrading-to-v0.3.0.md` states plainly: Codex can no longer
administer Hubu; owner actions happen on the portal or with `hubu` commands that
ask for Touch ID; stable upgrades are an owner action.

## 13. Testing

- **Route sweep.** Extend PR #423's table-driven test: every declared route is
  called with the agent credential and with the owner bearer under a refusing
  provider and under `X-Hubu-No-Prompt`, and the result matches its class. A route without a
  declaration fails the build.
- **Presence state machine.** Unit tests with a scripted provider cover:
  confirm, deny, timeout, unavailable, a confirmation not carrying over to the
  next action, tightening with the owner bearer and no prompt, concurrent prompt
  rejected, rate limit counting only refusals, owner-started approval denied

## 14. Known limits after v0.3.0

| Limit | Closed by |
| --- | --- |
| Agents on one macOS user can read each other's credential files | v0.3.1 attestation investigation, or a deployed Hubu |
| Executor routes accept the owner bearer, so an agent that reads it can call claim, settle and release | v0.3.2 signed authorizations and executor credential |
| Provider keys readable through `/usr/bin/security` if "Always Allow" was granted | v0.3.2 vault |
| An agent can edit the SQLite database directly | v0.3.3 tamper evidence |
| An agent can start its own `hubu-server` against the owner's database with a provider it controls, which is equivalent to a direct database edit | v0.3.3. Input for that spec: the anchor must not be forgeable by a rogue server. |
| The owner can be tricked into confirming a prompt an agent triggered | Out of scope (social engineering). Reason text and rate limits reduce it. |
| With the password fallback, a same-user process that has Accessibility permission and knows the login password could type it into the dialog | Stated limit. An owner who wants Touch ID only can set `HUBU_OWNER_PRESENCE_POLICY=biometrics`, which drops the password fallback. |
| Owner actions need a GUI session | Passkeys with the deployed version |
